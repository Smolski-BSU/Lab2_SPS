# Лабораторная работа №2. Service Profit Simulator

**Файл для сдачи:** `SPS.Student/ProfitAwareSystemPolicy.cs`, класс `ProfitAwareSystemPolicy : ISystemPolicy`.
В том же файле лежит вложенная RPC-политика `AdaptiveRpcPolicy` (развитие `AdaptiveRequestPolicy` из лабы №1).
Файл зависит только от `SPS.Abstractions`.

## Как запустить

1. Открыть `SPS.sln` (Visual Studio или `dotnet`, нужен .NET 8).
2. В `SPS.Runner/Program.cs` фабрика уже переключена: `CreateStudentPolicy() => new ProfitAwareSystemPolicy();`
3. Запустить `SPS.Runner` (интерактивно спросит seed) или `dotnet run -c Release --project SPS.Runner -- --seed 42`.

Дополнительно добавлен проект `SPS.Bench` (для сдачи не нужен, в `SPS.sln` не входит, запускается командой ниже): прогоняет стратегию на открытом сценарии
и своих сценариях с отказами и сравнивает с примером. Набор `stress` содержит 11 стресс-сценариев (см. раздел «Проверки»):

```
dotnet run -c Release --project SPS.Bench -- mine all 20
dotnet run -c Release --project SPS.Bench -- sample all 20
dotnet run -c Release --project SPS.Bench -- mine stress 20
```

## Решения и почему они такие

### 1. Бюджет обработки (`GetProcessingBudget`)
Бюджет = верхняя граница терпения из условия (Metadata 1.5 с, Preview 3 с, Generate 60 с).
Ушедший клиент не отменяет работу сам, а бюджет снимает его работу из очередей API, базы и воркеров.
Сильнее всего это помогает Generate: задание, которое уже никто не ждёт, не занимает воркер.

### 2. Кэш (`OnCacheRead`, `OnCacheFill`)
* Запись выдаётся, только если к моменту доставки (+2 мс) её возраст не превысит `MaxDataAge` **этого** клиента.
* Иначе клиент присоединяется к самой свежей идущей загрузке ключа. Данные будут прочитаны после её старта,
  поэтому они свежие, а база не получает лишней работы. База общая и не масштабируется, поэтому объединение
  загрузок дало самый большой выигрыш при перегрузке (+290 Profit на adv-heavy).
* TTL = максимальное встреченное требование свежести для типа минус текущий возраст. Дольше хранить запись
  бессмысленно: она никому не подойдёт.
* При нехватке памяти сначала вытесняются бесполезные (слишком старые) записи, затем записи с наименьшей
  популярностью на байт (популярность считается затухающим счётчиком с полупериодом 8 с). Новая запись
  сохраняется, только если она ценнее вытесняемых.

### 3. Задания Generate (`SelectJobAssignment`, `ReviewJob`)
* Ценность задания = `цена × P(клиент ещё ждёт к моменту готовности) − цена воркера × время работы`.
  Терпение считается равномерным на [15, 60] с, оценка работы берётся из `EstimatedWorkSeconds / скорость воркера`.
* Назначается задание с наибольшей ценностью **на секунду работы** самому быстрому свободному воркеру.
  Сравнивались FIFO, LIFO и варианты с затуханием, и этот вариант оказался лучшим.
* Задания, которые точно не успеют, отклоняются (`Reject`).
* Восстановление: задание переназначается, если воркер остановлен или признан мёртвым, а также если
  живой воркер шлёт heartbeat, но в них нет этого задания. Так бывает в двух случаях:
  * назначение потерялось в сети, и heartbeat про задание не было ни разу;
  * задание выполнялось, но пропало из heartbeat, а результата нет. Так происходит, когда очередь базы переполнена
    и публикация результата отброшена. Без переназначения воркер числился бы занятым и простаивал до конца
    бюджета клиента (до 60 с). Пока задание на воркере (в том числе ждёт базу), каждый доставленный heartbeat
    обновляет и время задания, поэтому ложных срабатываний нет. Этот случай найден при повторной проверке
    и исправлен: на сценарии с маленькой очередью базы Profit вырос с 1806 до 2330, на остальных не изменился.
  В остальных случаях стратегия ждёт: раннее переназначение создаёт дубли работы.

### 4. Мощности (`ReviewCapacity`)
* **Воркеры.** Ожидание задания до 15 с (минимальное терпение) ничего не стоит. Поэтому нужное число воркеров
  считается EDF-оценкой: минимальное `m`, при котором все выгодные задания очереди успевают к сроку
  «приход + 15 с». Оценка берётся не меньше 0.8 × средней нагрузки (поток заданий × средняя работа).
  Лишние воркеры выводятся раз в секунду и только незанятые: занятый может не успеть доделать задание за время вывода.
  Без заданий воркеров 0. Это дало около +5% Profit по сравнению с правилом «нагрузка + запас».
* **API.** Один API справляется с потоком (работа 10–15 мс, 4 слота). Второй добавляется,
  только если вызовы копятся. В хвосте прогона, когда запросы перестали приходить, API выключается.
  Один API вместо двух дал около +28 Profit, и на сценарии с падением API это не хуже.
* **Упавшие экземпляры.** Сначала поднимается замена, а мёртвый экземпляр пока остаётся в счёте.
  Так новый получает другой порядковый номер и не попадает под тот же сбой (сбои в эмуляторе привязаны к номеру).
  Через 2.5 с мёртвый выводится, и деньги за него больше не списываются.

### 5. Здоровье (`ReviewEndpoint`)
* **API:** три неудачи подряд за 2 с (тайм-аут или недоступен) переводят его в режим `Probe`
  (трафик закрыт, идут пробы). Трафик возвращается после быстрой успешной пробы. `Rejected` значит
  «жив, но перегружен» и неудачей не считается.
* **Воркер:** если heartbeat не приходил дольше 2.2 интервала, отправляется проба. Ответ `Success` (воркер свободен) или
  `Rejected` (занят) означает, что воркер жив и потерялись только heartbeat'ы. Тайм-аут пробы означает,
  что воркер мёртв. Так падение отличается от `HeartbeatIsolation`, и задания не дублируются зря.

### 6. RPC-политика (`AdaptiveRpcPolicy`, из лабы №1)
* Тайм-аут считается как `srtt + 8·rttvar`, отдельно для каждого типа запроса (EWMA как в TCP),
  с ограничением снизу (0.36 с для Metadata, 0.48 с для Preview, 0.6 с для Generate) и сверху **10 с**.
  В лабе №1 верхняя граница была 1 с. Тайм-аут не больше оставшегося терпения клиента. Тип и время прихода запроса
  известны, потому что общая стратегия передаёт их перед вызовом `GetTimeout`.
* Длинные тайм-ауты оказались выгоднее коротких. Тайм-аут не отменяет работу на сервере, поэтому
  ранний повтор при замедлении базы только удваивает нагрузку, а поздний ответ выбрасывается.
* Повторы делаются, пока клиент может дождаться ответа. Для Metadata и Preview не больше 5 попыток и есть бюджет
  повторов (token bucket, как в лабе №1). Регистрация Generate идемпотентна, поэтому повторов до 30.
  После `Rejected` (перегрузка) делается пауза.

## Проверки

* **Сборка.** Release и Debug: 0 ошибок, 0 предупреждений. С анализаторами `AnalysisLevel=latest-recommended` в файле
  решения тоже 0 предупреждений.
* **Требования к сдаче.** Один файл, единственная зависимость `using SPS.Abstractions;`. Движок, абстракции
  и пример стратегии не изменены. Из файлов репозитория изменена одна строка в `SPS.Runner/Program.cs` (фабрика `CreateStudentPolicy`, как сказано в README), остальное - новые файлы.
* **Детерминизм.** Два прогона с одинаковыми seed дают побайтно одинаковый вывод. Своих случайных генераторов
  в стратегии нет, используется только `Random`, который передаёт движок.
* **Скорость.** 220 прогонов (11 сценариев × 20 seed) идут около 15 с, то есть около 70 мс на прогон.
* **Обычный запуск.** `SPS.Runner --seed 42`: Profit 786.55, Metadata 100%, Preview 99.6%.
* **50 seed вместо 20** (сумма средних по 11 сценариям): моя стратегия 13 740, пример 2 130. Порядок результатов тот же, что на 20 seed.

## Что пробовалось и не вошло
* RPC-политика из лабы №1 без изменений (`AdaptiveRequestPolicy`, `MaxTimeoutMs = 10000`) вместо вложенной адаптированной.
  Работает почти так же, но в сумме по сценариям примерно на 0.3% хуже: она не знает тип запроса и оставшееся терпение клиента.
* Сокращение бюджета Metadata и Preview при перегрузке базы: без выигрыша.
* Убийство «медленных» воркеров (замедление ×4): Profit стал хуже. Новый экземпляр часто получает тот же
  порядковый номер и снова попадает под сбой.
* Задержка вывода простаивающих воркеров (гистерезис 2–4 с): без выигрыша.
* Короткие бюджеты обработки и отказ от повторов после `Rejected`: в пределах шума.
* Продление загрузки до срока самого позднего присоединившегося клиента (повторы и тайм-аут считаются
  не по первому клиенту загрузки). На перегруженной базе стало хуже на 80: лишние повторы добавляют ей работы,
  а на остальных сценариях выигрыш около +1.
* Учёт замедленных воркеров по фактическому времени заданий (назначать задания более быстрым, пересчитывать ценность).
  При долгих замедлениях это даёт +17…+34, но при коротких (10 с) теряет −14. Замедление обнаруживается
  с опозданием, когда сбой уже закончился. Итог около нуля, а код сложнее, поэтому не вошло.
* Выбор, какой экземпляр выводить: сначала самый медленный незанятый воркер или самый медленный API.
  Результат в пределах шума (±8 на сумме 13 890).
